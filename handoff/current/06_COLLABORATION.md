“继续推进项目”表示接续当前授权范围，先核对已完成事项与下一项；不从零重建，不重复已完成工作，不反复确认常规可逆步骤。确需用户决定时，先完成必要准备，使结果具体可审阅；问题用普通文字，不发选项卡。

缺失时机、目标、费用、秘密字段、失败处理或落位规则时，登记具体缺口，推进不依赖缺口的已确认部分。暂停队列和恢复授权以STATE为准，普通“继续”不自动恢复另行暂停的整盘测试、模式独立适配、最终视觉或APK工作。

## 3. 先确定影响，再选择验证

每轮简短说明具体问题、影响模块及验证范围，先做“确认规则→现有行为→差分”映射。按实际依赖核对公共身份、当前控制方与秘密信息、行动历史、正式回合与子行动、持续计数、消灭批次、空间落位、终局及命令重放；这些是影响分析维度，不是每轮机械执行的全套清单。

持续和延迟效果核对获得时点、首次计时、剩余机会及刷新/离开/到期顺序。读取秘密身份须有明确来源。UI按批准参考图及授权范围修改，不为工具方便重绘、重排。

## 4. 测试执行与重复控制

保留有价值的旧用例，精简执行次数；不以测试数量证明工作量或完整验收。不为可逆、低影响调整增加测试，也不增加只复述实现的断言。

| 改动或阶段 | 默认验证 | 扩大条件 |
| --- | --- | --- |
| 纯协作文档、导航、来源登记 | 差分、链接、JSON与摘要一致性 | 涉及正式规则或合同，另做语义影响分析 |
| 局部英雄或规则修复 | 缺陷情景、边界及关联回归 | 共享层变化、跨机制失败或未解决问题 |
| 公共身份、回合、死亡、空间、终局等 | 开发中跑相关套件；一批修改完成后跑一次全套引擎回归 | 后续改动、失败或未解决风险 |
| 按钮、输入、页面及命令接入 | 必要构建、受影响的真实浏览器操作 | 公共流程变化或阶段收尾 |
| 阶段提交或发布检查点 | 一次最终全套回归、必要构建，核对实际提交CI | 当前版本缺有效证据时补跑 |
| Android嵌入资源变化 | 构建输出与嵌入资源同步、一致性 | APK与实机按阶段授权执行 |

执行约定：

- 可稳定复现的缺陷尽量保留修复前失败、修复后通过的用例；简单调整不强制制造失败测试。
- `npm run check`和`verify-invariant-evidence.mjs`都会跑全套引擎测试，同一版本不为取得另一种报告连续跑两遍。需要合同证据时优先后者，构建另按需要执行。
- 引擎与浏览器可检查同一机制的不同层次，分别说明权威结算和控件接入，不能算两份完整玩法验收。小改动不机械重跑无关模式检查，阶段收尾或相关依赖变化再扩大。
- 本地最终回归与CI独立环境、实际提交核对有价值；避免同一源码反复触发。文档HEAD变化不自动使旧产品证据失效，核对相关源码、合同和构建依赖是否变化。既有必需CI和仓库检查仍要遵守。
- 检查通过后，仅因新改动、失败或未解决问题扩大或重复运行。日志截断先读完整日志和退出状态，不能据不完整输出声称通过；无法确认执行完成才补跑。
- 失败先区分产品、测试夹具、环境或网络原因，修复实际原因后补必要验证，保留真实失败记录，避免盲目重试。
- CI触发优化已独立实施，详见26_CI_SCOPE_2026-10-08.md。范围选择须保留必要检查与失败可见性；前驱未确认成功时保守运行全部检查。
