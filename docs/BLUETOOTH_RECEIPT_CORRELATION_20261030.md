# 蓝牙等待态与请求关联｜2026-10-30

实施前设计：复用现有 v2 `action → ping(id) / pong(id)`，不增加协议字段、不改变 snapshot/error 载荷或编号，不把快照当作请求确认。来宾在实际 action 发送后，沿同一连接发送同请求编号的 ping；房主原处理器同步处理每条 action 后才处理下一条 ping 并 echo pong。只在收到当前编号的 pong 后解除等待，并用当前视图刷新控制状态。任意快照、旧错误、旧 pong 不能清除此等待。规则错误仍保留原提示，等待到其后 pong。

兼容范围：旧 v2 房主已有 ping/pong 分支，旧来宾不使用此等待路径；新来宾/旧房主及新来宾/新房主均使用同一既有格式。PR20 错误后最新已提交快照继续保留；旧房主的错误无快照缺陷不因本修复得到逆向修正。

语义严格限于单条正常有序连接中的处理顺序。pong 不包含接受/拒绝/duplicate 结果，不是规则接受 ACK，也不证明丢失/失败的原 action 已进入权威；快照仍只渲染最新收到的授权视图。不同连接生命周期由现有原生状态清等待和编号；不重发、不补交、不自动恢复未知结果。Java send 捕获 IOException 后异步 transport-error，可能未提交 action 却仍能送出后续 ping；本轮要以明确故障注入证明这个限制，后续单独设计可核证的投递结果。不得据此宣称完整 exactly-once、跨连接排序或真机验收。

同步 action 发送抛错时清本次等待；action 已发而 ping 同步发送失败时保留等待并提示连接恢复，避免把不确定结果改报规则拒绝。真实 IOException、原生 UI 渲染、radio 尚无运行证据。

本轮只改 web/app.ts 消费者和离线驱动/回归/审计；src 游戏权威、门禁、英雄、素材、评分冻结和 NET 暂停保持。使用真实 BluetoothHostRoom、实际生产 applyBluetoothView/消息函数，DOM 最终渲染及 native send 为记录替身。队列按产生顺序释放；原队列延迟与人为失败/重复控制必须分别记证，不能冒充原自然棋谱或半混乱客户端验收。
